1. 四层数据架构

L4 展示缓存层 DisplayCache ← 内存驻留，UI 直接消费 当前成员的最新 FusedMetric 快照 APP 启动时预热，后台释放 ───────────────────────────────────────────── L3 融合层 FusionLayer ← 实时计算，不持久化 MetricFusionEngine 按策略选择最佳值 输入 L2 → 输出 FusedMetric → 写入 L4 ───────────────────────────────────────────── L2 原始数据层 RawDataLayer ← SQLite 持久化 所有设备的每次读数，不可变，只追加 带 profileId + source + schemaVersion ───────────────────────────────────────────── L1 设备通信层 DeviceLayer ← 瞬态，不持久化 BTService / rPPG / 其他 SDK 的原始回调 转换为 RawReading 后交给 L2

L1 设备通信层

SDK 回调的原始数据，格式各异。瞬态，不持久化。由各 Service 接收并转换为 RawReading。

瞬态

L2 原始数据层

所有测量结果的永久存储。只追加，不修改，不删除。SQLite 持久化。

持久化 不可变

L3 融合层

纯计算层。输入 L2 的 RawReading，按策略融合，输出 FusedMetric。不持久化（随时可重算）。

计算

L4 展示缓存

内存字典，当前成员的最新融合指标。APP 启动预热，通过 Combine 通知 UI 更新。

内存 Combine

3. SQLite 存储方案

5. Schema 版本管理

每条 RawReading 记录自身的 schemaVersion。不同版本的数据可以共存。数据库级别的迁移只处理表结构变更。

迁移机制

SchemaMigrationManager APP 启动 │ ├─ 读取 schema_version 表，获取当前版本 │ ├─ 与 currentVersion 对比 │ ├─ 相同 → 跳过 │ └─ 落后 → 逐版本执行迁移 │ └─ 每次迁移后记录到 schema_version 表

表结构变更（ALTER TABLE）

版本变更迁移方式
V1 → V2添加 source_version 字段ALTER TABLE ADD COLUMN
V2 → V3ECGPayload 添加 filterVersion无需改表（payload 是 JSON）

Payload 版本兼容规则

Payload 用 JSON 存储，天然支持向后兼容。严格遵守以下规则：
规则做法
允许 新增字段用 Optional 类型 + decodeIfPresent + 默认值
禁止 删除字段保留字段，标记 deprecated 注释
禁止 修改字段类型如 Int 改 String — 创建新字段代替
破坏性变更创建新的 Payload 类型（如 ECGPayloadV2）

写入保证

  • 串行队列：所有 SQLite 写入在 dbQueue 串行执行，保证顺序
  • 原子性：单条 INSERT，无需事务（只追加，无更新）
  • 先写后算：先持久化 RawReading，再触发融合计算
  • 主线程通知：Combine 通知切回主线程，UI 从 DisplayCache 读取
